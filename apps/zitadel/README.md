# zitadel

ZITADEL v4.20.3 identity provider with PostgreSQL on homelab k3s.

Purpose: single identity per person in the homelab — local login (password, passkey, 2FA) or linked external identity (GitHub). Apps talk to ZITADEL via OIDC.

## GitHub identity provider and mail

GitHub is a linkable identity provider (homelab#149 step 2): a person keeps one Zitadel user and can log in
with password or GitHub. GitHub never creates users (`isCreationAllowed: false`); a signed-in user links
GitHub once (Profile → linked identity providers).

- The Job `zitadel-configure-<hash>` runs `configure/configure.mjs` against the REST admin API inside the
  cluster (`http://zitadel:<service port>`, `Host` = `X-Zitadel-Public-Host` = `id.<domain>`): it creates or
  updates the GitHub provider, allows external identity providers in the default login policy and offers
  GitHub there. Idempotent; Pulumi waits for it, so a failure fails the deploy.
- It runs again when the script changes (the hash is in the name) or when `CONFIGURE_REVISION` in
  `src/index.ts` is raised, e.g. after rotating a value in ESC.
- Credentials come from Pulumi ESC `mrsimpson/homelab/dev` through the ExternalSecret `zitadel-github-idp`:
  `zitadelDeployKey` (the key file of the service account `homelab-deploy`, **base64-encoded as one line**),
  `zitadelGithubClientId`, `zitadelGithubClientSecret`.
- Mail: the same Job adds and activates an SMTP configuration for the in-cluster Mailpit
  (`mailpit-smtp.mailpit.svc.cluster.local:1025`, sender `zitadel@<domain>`, no TLS, no auth). Verification
  and password mails are read at `https://mail.<domain>` (apps/mailpit); they never leave the cluster.
- One-time owner steps (done 2026-11-20): GitHub OAuth app with callback `https://id.<domain>/idps/callback`;
  service account `homelab-deploy` with a JSON key and the instance role Instance Owner (`IAM_OWNER`).

## Deployment notes

- No oauth2-proxy in front: ZITADEL is the login itself (`AuthType.NONE`).
- Master key: generated at deploy time by Pulumi, encrypted in the stack's state. Never appears in the repository.
- First admin password: stored in a Kubernetes Secret (`zitadel-first-admin-password`), generated at deploy time from a Pulumi-encrypted secret with `minSpecial: 1, minUpper: 1, minLower: 1, minNumeric: 1` (guarantees every character class required by ZITADEL's default password complexity policy). The owner reads it once at first login (and changes it, because `ZITADEL_FIRSTINSTANCE_ORG_HUMAN_PASSWORDCHANGEREQUIRED=true`).
- Database: CloudNativePG via `PostgresInstance`. The init Job bootstraps schemas (`zitadel init schema`); the setup Job creates the first instance (`zitadel setup --masterkeyFromEnv --config /config/zitadel.yaml`).
- Login V2: ZITADEL v4.20.3 requires Login V2 for the console login to work. Login V2 is a Next.js app running on its own image (`ghcr.io/zitadel/zitadel-login:v4.20.3`), on port 3000. It authenticates to the core via X.509 certificate-based JWT (SystemAPIUsers mechanism) — an RSA keypair is generated once with `@pulumi/tls`, stored in a Kubernetes Secret, and mounted into both pods (private key for signing in login, public cert for verification in zitadel).
- Login V2 routing: the core `createExposedWebApp` uses `extraRoutes` to route `/ui/v2/login` to the Login V2 Service (port 8090, targetPort 3000). The longest prefix wins in Gateway API, so `/ui/console` routes to zitadel (port 8080) and `/ui/v2/login` routes to login. Login V2 reads its connection config from a `.env` file mounted at `/.env-file/`, which contains `ZITADEL_LOGINCLIENT_KEYFILE`, `AUDIENCE`, `ZITADEL_API_URL`, and `CUSTOM_REQUEST_HEADERS`.
- Session cookie: the Login UI signs its session cookies with a secret generated at deploy time via `@pulumi/random` (64 characters, no special chars).
- Login V2 init container: waits for the core zitadel to be ready using `wait4x` against `http://zitadel:<service-port>/debug/ready` (h2c), where `<service-port>` is the ExposedWebApp Service port (80, derived from `app.service.spec.ports[0].port`). The login `.env` ConfigMap uses the same port for `ZITADEL_API_URL`.
- Exposure: HTTPS at `id.<domain>` via the Cloudflare Tunnel / Traefik Gateway. The Service uses `appProtocol: h2c` for HTTP/2 to the pod.
- The Deployment runs `/app/zitadel start --masterkeyFromEnv --config /config/zitadel.yaml` (the root command refuses to run without a subcommand; `zitadel start` starts the server: cmd/start/start.go; `--config` is mandatory to read ExternalDomain, TLS, FirstInstance etc. from the ConfigMap: cmd/zitadel.go:56,97).
- Config file: mounted at `/config/zitadel.yaml` from a ConfigMap. Contains ExternalDomain, ExternalPort, ExternalSecure, TLS settings, AND the SystemAPIUsers.login-client entry (public cert path for JWT verification). FirstInstance settings (org name, admin user, email, password, PasswordChangeRequired) are passed as `ZITADEL_` environment variables to the setup Job — not from the config file, because `NewSteps` reads FirstInstance only from `ZITADEL_` env vars (cmd/setup/config.go:205-217).
- Health check: `GET /debug/healthz` on port 8080.
- No persistent storage needed: ZITADEL is stateless; all state is in PostgreSQL.
